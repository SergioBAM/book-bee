# Book Bee - Architecture

## 1. Architecture Goals

Book Bee is a native Android application designed around fast, reliable ownership checks for physical books.

The architecture should support:

- offline-first usage
- fast barcode scanning
- reliable ownership matching
- local data ownership
- isolated user libraries
- JSON backup and restore
- future Azure backend integration
- clean utility-first UI
- long-term maintainability without over-engineering

The MVP should remain simple, but the architecture should avoid decisions that make future cloud backup, sync, or metadata improvements difficult.

---

## 2. Core Technical Decisions

| Area | Decision |
|---|---|
| Platform | Native Android |
| Language | Kotlin |
| UI | Jetpack Compose |
| Local Database | Room / SQLite |
| Dependency Injection | Hilt |
| Barcode Scanning | CameraX + ML Kit Barcode Scanning |
| Architecture Style | Offline-first, layered architecture |
| Navigation | Pager/swipe-centric navigation |
| Backend | None for MVP, Azure later |
| Export Format | JSON |
| User Model | Local user abstraction, isolated libraries |
| Book Identity | Internal UUIDs, never external IDs |

---

## 3. Architectural Principles

### Offline First

The local database is the source of truth.

Book Bee must remain useful without network access. Network calls are used to enrich the local library, not to make core ownership tracking possible.

The app should support:

- scanning a book
- checking ownership
- browsing the shelf
- adding books manually
- editing books
- viewing wishlist items
- exporting data

without requiring an active backend.

---

### Internal Identity First

Every major local entity must use an internal ID generated by Book Bee.

External identifiers such as ISBNs, Google Books IDs, OpenLibrary IDs, or future Azure IDs must never be used as primary identifiers.

External identifiers can change, disappear, collide, or be missing. Internal UUIDs remain stable.

---

### Manual Data Is First-Class

Books added manually are not fallback records or incomplete objects.

A manually added book should behave the same as a scanned or metadata-enriched book.

This is important because metadata lookup may fail, ISBNs may be missing, and users may own older or unusual editions.

---

### Local Ownership Before Metadata Perfection

Book Bee is not trying to be a perfect bibliographic catalogue.

The primary question is:

> Do I own this book?

The system should prefer practical, reliable ownership decisions over complex metadata modelling.

---

## 4. High-Level Architecture

Book Bee uses a layered architecture:

```text
UI Layer
Jetpack Compose screens, navigation, UI state

Presentation Layer
ViewModels, screen state, user actions

Domain Layer
Use cases, ownership matching, business rules

Data Layer
Repositories, Room DAOs, metadata providers, import/export

Infrastructure Layer
Camera, barcode scanner, network clients, backup providers
```

The intended dependency direction is:

```text
UI -> Presentation -> Domain -> Data -> Infrastructure
```

Domain logic should not depend directly on Android framework APIs.

## 6. Data Model

### User

Even before real authentication exists, the app should model a user.

```kotlin
UserProfile
- id: UUID
- displayName: String?
- createdAt: Instant
- updatedAt: Instant
```

MVP may create a single default local user automatically.

This prepares the app for future Azure authentication and multi-device backup without forcing cloud accounts into the MVP.

---

### Book

A book represents the conceptual work or edition-level record stored by the user.

```kotlin
Book
- id: UUID
- userId: UUID
- title: String
- subtitle: String?
- authors: List<String>
- normalizedTitle: String
- normalizedAuthors: List<String>
- description: String?
- publisher: String?
- publishedDate: String?
- pageCount: Int?
- thumbnailUrl: String?
- createdAt: Instant
- updatedAt: Instant
```

Manual books are valid even when most metadata fields are empty.

---

### BookIdentifier

External identifiers are stored separately.

```kotlin
BookIdentifier
- id: UUID
- bookId: UUID
- type: IdentifierType
- value: String
```

Example identifier types:

```kotlin
ISBN_10
ISBN_13
GOOGLE_BOOKS_ID
OPEN_LIBRARY_ID
OTHER
```

ISBNs are important for matching but are not primary keys.

---

### Ownership

Ownership represents the user owning a book.

For MVP, multiple copies are represented by quantity.

```kotlin
Ownership
- id: UUID
- userId: UUID
- bookId: UUID
- quantity: Int
- status: OwnershipStatus
- dateAdded: Instant
- archivedAt: Instant?
- notes: String?
- createdAt: Instant
- updatedAt: Instant
```

Ownership statuses:

```kotlin
OWNED
ARCHIVED
```

Read status can either live on `Ownership` for MVP or in a separate reading table later.

For MVP:

```kotlin
ReadStatus
- UNREAD
- READING
- READ
```

---

### WishlistItem

```kotlin
WishlistItem
- id: UUID
- userId: UUID
- bookId: UUID
- notes: String?
- priority: Int?
- createdAt: Instant
- updatedAt: Instant
```

A wishlist item should reference a book record so metadata can be reused between shelf and wishlist.

---

### MetadataLookupCache

Metadata lookups should be cached locally.

```kotlin
MetadataLookupCache
- id: UUID
- provider: MetadataProvider
- lookupType: LookupType
- lookupValue: String
- responseJson: String
- createdAt: Instant
- updatedAt: Instant
```

This reduces repeated API calls and supports debugging metadata behaviour.

---

## 7. Local Storage

Book Bee uses Room backed by SQLite.

Room should store:

- user profiles
- books
- identifiers
- ownership records
- wishlist items
- metadata cache
- import/export history if needed later

Room migrations should be treated seriously from the start, even during MVP development.

Destructive migrations may be acceptable during early private testing, but once real user data exists, migrations should preserve data.

---

## 8. Barcode Scanning Flow

Book Bee uses a deliberate scan flow.

```text
User taps Scan
Camera opens
ML Kit detects barcode
Scanner accepts first valid ISBN barcode
Haptic feedback fires
Camera/scanner freezes
App navigates to scan result
Ownership check runs
Metadata lookup runs if needed
Result is displayed
```

The scanner should not continuously process multiple books in a single session.

After a successful scan, the user should explicitly choose to scan again.

---

## 9. Metadata Lookup

The metadata lookup system should be provider-based.

Initial provider order:

```text
1. Google Books
2. OpenLibrary
3. Manual entry fallback
```

A shared interface should hide provider-specific details:

```kotlin
interface BookMetadataProvider {
    suspend fun lookupByIsbn(isbn: String): BookMetadataResult
}
```

Provider responses should be mapped into internal models before reaching the domain layer.

The app should not leak provider-specific models into UI or domain code.

---

## 10. Ownership Matching

Ownership matching determines whether the user likely owns a scanned or searched book.

Possible results:

```kotlin
OwnershipMatchResult
- Owned
- LikelyOwned
- NotOwned
```

---

### Exact Match

An exact match occurs when the scanned ISBN matches an existing stored ISBN.

Result:

```text
Owned
```

The app may show:

- matching book
- quantity
- date added
- read status

---

### Fuzzy Match

A fuzzy match occurs when ISBN does not match but title and author are similar enough.

Matching should use:

- normalized title
- normalized authors
- punctuation stripping
- casing normalization
- token comparison
- edit-distance similarity
- weighted title/author score

Suggested weighting:

```text
Title: 70%
Author: 30%
```

Result:

```text
Likely Owned
```

The UI should show the matching owned book and allow the user to confirm whether it is the same book.

---

### Not Owned

If no exact or fuzzy match is found, the result is:

```text
Not Owned
```

The user should then be able to:

- add to shelf
- add to wishlist
- edit metadata before adding
- scan again

---

## 11. Search

Shelf and wishlist search should use local data first.

Search should cover:

- title
- author
- ISBN
- notes

For MVP, Room queries and normalized text fields are enough.

Full-text search may be added later using SQLite FTS if needed.

---

## 12. Import and Export

Book Bee exports data as JSON.

JSON export should include everything required to reconstruct the local library:

- user profile
- books
- identifiers
- ownership records
- wishlist items
- read status
- notes
- metadata cache, if useful
- schema version
- export timestamp

The export should not intentionally omit data to save space.

Data safety matters more than small file size.

---

### Export Format

The export should include a schema version.

```json
{
  "schemaVersion": 1,
  "exportedAt": "2026-05-09T00:00:00Z",
  "app": "Book Bee",
  "users": [],
  "books": [],
  "identifiers": [],
  "ownership": [],
  "wishlist": [],
  "metadataCache": []
}
```

---

### Import Modes

Book Bee should support two import modes.

```text
Replace
Merge
```

---

### Replace Import

Replace import deletes the current local library and restores from the selected JSON file.

The UI must clearly warn the user before replacing data.

---

### Merge Import

Merge import combines imported records with existing local records.

Merge should use internal IDs when available.

If internal IDs collide, imported records should update existing records only when this is clearly safe.

If internal IDs do not match, the app may use ISBN and fuzzy matching to detect likely duplicates.

Merge behaviour should be conservative. Avoid silent data loss.

---

## 13. Backup and Restore

For MVP, backup and restore are local JSON workflows.

Future cloud backup should build on the same export/import foundation.

Initial backup targets may include:

- Android system file picker
- user-selected folder
- cloud provider folder through Android storage access framework

True cloud sync is not part of MVP.

---

## 14. Future Azure Backend

Azure integration is intentionally deferred.

The app should avoid hard-coding backend assumptions until the Azure ecosystem is better understood.

Future Azure options may include:

- Azure App Service
- Azure Functions
- Azure SQL
- Cosmos DB
- Blob Storage
- Azure AD B2C or Microsoft identity services

For now, the architecture should expose cloud-facing interfaces without implementing them.

Example:

```kotlin
interface BackupRepository {
    suspend fun exportBackup(): BackupFile
    suspend fun importBackup(file: BackupFile, mode: ImportMode): ImportResult
}
```

Later Azure support can implement the same contracts.

---

## 15. UI Architecture

Book Bee uses Jetpack Compose with a pager/swipe-centric navigation model.

Primary sections:

```text
Shelf
Scan
Wishlist
```

The app should feel similar to horizontally swiping between home-screen pages.

The active section title should remain clear.

The bottom area can be reserved for contextual controls and primary actions.

---

### UI Principles

The UI should be:

- clean
- fast
- readable
- utility-first
- low-friction
- calm
- information-dense without feeling cluttered

Book covers are secondary.

Ownership status and actions are primary.

---

## 16. Presentation Pattern

Each feature should use ViewModels exposing immutable UI state.

Example:

```kotlin
data class ShelfUiState(
    val books: List<ShelfBookUiModel>,
    val searchQuery: String,
    val isLoading: Boolean,
    val errorMessage: String?
)
```

ViewModels should expose:

```kotlin
StateFlow<UiState>
```

User actions should be represented explicitly:

```kotlin
fun onSearchChanged(query: String)
fun onBookSelected(bookId: UUID)
fun onAddBookClicked()
```

Avoid placing business logic directly inside Composables.

---

## 17. Error Handling

Book Bee should treat failure as normal.

Examples:

- barcode scan succeeds but metadata lookup fails
- network unavailable
- provider returns incomplete data
- import file is invalid
- duplicate book is detected
- fuzzy match is uncertain

The app should provide a useful next action instead of blocking the user.

For metadata failures, the user should be able to:

- retry lookup
- add manually
- edit scanned ISBN
- cancel
- continue without metadata

---

## 18. Privacy and Security

Book Bee libraries are private by default.

MVP data remains local unless the user explicitly exports or backs it up.

Future cloud features should require explicit user action and clear explanation.

The app should avoid collecting unnecessary analytics or behavioural data.

If telemetry is ever added, it should be opt-in.

---

## 19. MVP Scope

The MVP should include:

- local user profile
- shelf
- wishlist
- barcode scanning
- ISBN metadata lookup
- manual add
- exact ISBN ownership matching
- fuzzy title/author ownership matching
- quantity support
- read status
- JSON export
- JSON import with replace and merge
- local-first Room storage
- clean Compose UI

---

## 20. Explicitly Out of Scope for MVP

The MVP should not include:

- social features
- recommendations
- price tracking
- lending tracking
- full cloud sync
- multi-device conflict resolution
- advanced reading analytics
- decorative bookshelf UI
- complex collector-grade edition modelling

These may be considered later, but they should not distract from the core ownership-checking workflow.

---

## 21. Future Architecture Considerations

Possible future improvements:

- Azure backup provider
- true multi-device sync
- conflict resolution
- SQLite full-text search
- improved fuzzy matching
- metadata reconciliation
- price comparison
- wishlist price alerts
- lending tracking
- richer reading history
- import from other book apps
- Play Store distribution

Each future feature should preserve the core product principle:

> Book Bee is a fast, practical utility for knowing whether you already own a book.
